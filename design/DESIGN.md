## 0. 依据与局限

### 0.1 参照素材

`design/references/` 共 4 张 Linear 桌面端截图，覆盖了四种典型界面（议题详情 + 侧栏、Pulse 信息流、收件箱三分栏、看板 + 评论浮层）。这四张足以提取视觉语言，因为**它们在结构上差异很大，但视觉规则完全一致**——这本身就是"设计语言"存在的证据。

### 0.2 现状素材

我离屏渲染了当前应用的全部 5 个页面作为对照基准，命令可复现：

```powershell
$env:QT_QPA_PLATFORM='offscreen'; python -c "
import sys, os; sys.path.insert(0, os.getcwd())
from PySide6.QtWidgets import QApplication
from ui.main_window import MainWindow; from ui.theme import APP_STYLESHEET
app = QApplication(sys.argv); app.setStyle('Fusion'); app.setStyleSheet(APP_STYLESHEET)
w = MainWindow(); w.resize(1180, 760); w.show()
for i, n in enumerate(['p0','p1','p2','p3','p4']):
    w.sidebar.setCurrentRow(i); app.processEvents(); w.grab().save(n + '.png')
"
```

> **重要局限：离屏环境没有中日韩字体，截图中的汉字与韩文全部渲染为方块（tofu）。**
> 因此本轮的对照结论**只覆盖布局、色彩、间距、密度、层级**，**不包含字形质量、字重表现与中文排版细节**。后者需要在真实窗口中人工确认，见第 7 章。

### 0.3 关于 Linear 色值

下文列出的 Linear 色值是从截图中**读取的近似值**，不是 Linear 的官方设计 token（他们未公开）。落地时应当遵循**关系**而非**精确 hex**——即"面板比背景亮几档""边框比底色亮几档""强调色占多大面积"，而不是去凑某个具体数值。

## 1. Linear 视觉语言提取

从 4 张截图中共通的部分，可以拆出 9 条规则。这是本文档要移植的东西。

| # | 规则 | 具体表现 |
|---|---|---|
| L1 | **底色只有几档，且阶差极小** | 应用底 ≈ `#0D0E10`，面板 ≈ `#131417`，抬升层 ≈ `#191A1E`，选中 ≈ `#202127`。相邻两档的明度差**几乎察觉不到**，层级靠累积而非跳跃 |
| L2 | **层级由 1px 边框承担，而不是阴影** | 全界面几乎零阴影。面板、卡片、输入框、列表分组、浮层，全部用同族 1px 边框（≈ `#232529`）划分。边框只比底色亮一档 |
| L3 | **侧边栏窄且不抢戏** | 宽约 232–244px。侧边栏底色与应用底几乎同色，选中项只是一个极淡的填充块（≈ `#1A1B1F`）。**没有强调色填充、没有左侧色条、没有加粗** |
| L4 | **圆角小** | 列表行 / 按钮 / 标签 4–6px，面板 8px，浮层 10–12px。仅胶囊型 tab 用全圆角 |
| L5 | **字号跨度窄，层级靠颜色而非字号** | 正文 13–14px，页面标题 20–22px，小节标题 14–15px。整个界面字号跨度只有约 8px。区分层级主要靠**文字明度**（#E8E8E8 / #8A8F98 / #5C6068） |
| L6 | **强调色极少、面积极小** | 全界面唯一强调色是靛蓝 ≈ `#5E6AD2`，只出现在发送按钮、少数标记上，单个出现面积通常 < 1% 屏幕。**大面积区域一律无彩色** |
| L7 | **状态色永远伴随图形，不单独承载语义** | "Project on track" 是绿色图标 + 文字；标签是彩色小圆点 + 文字。颜色是冗余信息，不是唯一信息 |
| L8 | **密度高但受控** | 导航行高 ≈ 30px，双行列表行 ≈ 48–52px，区块间距 8/12/16/24。信息多，但每个元素都有明确呼吸空间 |
| L9 | **图标是单色线性、统一尺寸** | 16px 线性图标，颜色与相邻次要文字同色（#8A8F98）。**没有一个彩色图标、没有一个 emoji** |

**一句话概括：** Linear 的"高级感"不来自装饰，来自**克制的一致性与精确的阶差**——颜色少、圆角小、阴影无、边框贯穿、字号跨度窄，靠极小但严格的明度差建立秩序。

## 2. 现状对照 · 10 个最明显的视觉差异

按视觉冲击力排序。每条给出**截图证据 → Linear 做法 → 差距性质**。

### 差异 1 · 明度方向完全相反

**现状：** 暖白底 `#F7F8F4` + 纯白卡片 `#FFFFFF` + 深绿侧栏 `#173E36`。
**Linear：** 近黑底 `#0D0E10`，面板抬升到 `#131417`，全靠 1px 边框分界（L1 / L2）。
**性质：** 根本性。浅色底意味着**必须先有高对比才能看清结构**，于是白卡片靠明度差（#FFF vs #F7F8F4，仅 3% 明度差但面积巨大）撑起层级，视觉上是"飘"的；而 Linear 是"压"的。其余 9 条差异大半是这一条的衍生。

### 差异 2 · 侧边栏：宽、且选中态极其高调

**现状：** 宽 224px；选中项是整块**高饱和金 `#E0AA55` 填充 + 深绿反白加粗字**（见截图 p0/p1/p3/p4 中那块琥珀色），对比度是全界面最高的元素之一，即使它只是导航。另外侧边栏底部渲染出了**水平滚动条**（5 张截图均有，见侧栏底部的小箭头），是明确的缺陷。
**Linear：** 侧栏底色与应用底几乎同色；选中项只是 `#1A1B1F` 的淡填充，**颜色与会抢走注意力的元素恰恰相反**（L3）。
**性质：** 方向相反。当前实现把"强调色"用在了最高频、最低信息量的元素上，导致每切一次页面都闪一次大面积色块。

### 差异 3 · 圆角过大，偏"消费级软感"

**现状：** 卡片 16px、导航项 10px、按钮 9px（`ui/theme.py`）。
**Linear：** 面板 8px、行/按钮 4–6px（L4）。
**性质：** 数值级别。16px 圆角配上本就宽松的留白，整体读起来是"柔和、亲和、消费级 App"，而 Linear 的 4–8px 是"精密、工具、专业"。

### 差异 4 · 信息密度过低，且间距没有栅格

**现状：**
- 页面外边距 **42px**（P0/P2），另一套页面是 **20px**（P1/P3/P4）——两套并存
- 卡片内边距 22/20/22/18，卡片间距 14~18
- 导航项 padding 12/14（行高约 44px），指标卡 `min-height: 86px`
- 全文档出现的间距值：`42 / 34 / 28 / 22 / 20 / 18 / 14 / 12 / 9 / 5` ——**无栅格**

**Linear：** 基准 4/8 的倍数，区块 8/12/16/24；导航行高 ≈30px（L8）。
**证据：** 截图 p0 中，1180×760 的窗口里只装下 4 张指标卡 + 一个几乎空的任务卡；首屏有效信息量远低于 Linear 同等面积。
**性质：** 数值 + 系统性。"较高但受控的信息密度"这一条当前完全不满足；间距值任意而非成体系，是"不够精确"的根源。

### 差异 5 · 字号层级跨度过大

**现状：** 页面标题 **27px**、指标数值 **25px**、品牌名 20px、卡片标题 16px、正文 13–14px。跨度约 **15px**（`PRODUCT_SPEC` 3.2）。
**Linear：** 正文 13–14、标题 20–22，跨度约 **8px**；层级主要靠**文字明度**区分（L5）。
**性质：** 方法不同。当前靠"字号差"建立层级，结果是标题在抢戏、全局节奏被几个大字号锚点拉散；Linear 靠"明度差"，字号变化小但层级依然清楚。

### 差异 6 · 两套互不相干的高饱和调色板并存

**现状：** 主题是绿色系（`#1F6B57` 主按钮），但 P1 用 **`#f39c12` 亮橙**、P4 用 **`#9b59b6` 亮紫** 的平铺满色按钮（截图 p1/p4 中极其扎眼的两块）。这两个颜色与绿色体系、与"低饱和"要求都没有关系——是遗留的内联样式。
**Linear：** 全界面只有一个强调色，且面积极小（L6）。
**性质：** 一致性崩溃。这是**当前最容易被一眼看出的问题**，也是唯一一个"纯粹是 bug 而不是取舍"的差异。

### 差异 7 · 次级按钮几乎不可见——把"克制"做成了"淡"

**现状：** `iconButton` = 米色底 `#F6F2E9` + 棕字 `#8A5A19`。而页面底色是 `#F7F8F4`——**按钮底色与页面底色只差 3% 明度**，边界完全消失（截图 p2 中那一排若隐若现的胶囊）。
**Linear：** 次级按钮是**深灰底 + 1px 边框**——对比度依然低，但**边界清晰**（L2）。
**性质：** 对"克制"的误解。Linear 的"低对比"指的是**层级低**（不与主按钮竞争），不是**看不见**。当前实现同时失去了层级和可发现性，这是最需要纠正的认知偏差。

### 差异 8 · 边框语言缺失

**现状：** 全局只有一种边框色 `#E4E9E4`，只用在卡片和输入框上；白卡片浮在暖白底上主要靠明度差，而不是边框；列表分割线用 `#EDF0EC`（又是一种颜色）。
**Linear：** 同族 1px 边框**贯穿所有层级**——面板、卡片、输入框、列表分组、浮层，且只比底色亮一档（L2）。
**性质：** 缺失的机制。当前是"偶尔用一下边框"，Linear 是"用边框构成整个空间结构"。

### 差异 9 · 用 emoji 充当图标

**现状：** `📂 🔍 📝 ✂️ 🗂️ 📕 🎵 🎞️ 📊 ✅ ❌` 散布在按钮、列表项、标题（如 `✂️ 知识碎片画廊`）、状态提示中。emoji 天然彩色、尺寸不一、随系统字体变化。
**Linear：** 全部为 16px 单色线性图标，颜色跟随相邻文字（L9）。
**性质：** 直接冲突。emoji 是"低饱和克制"最直接的破坏者——单个彩色 emoji 的饱和度往往高于整个界面其余部分之和。

### 差异 10 · 状态语义色缺失，焦点反馈过重

**现状：** 成功 / 失败 / 警告用 `✅`/`❌` emoji + 感叹号硬编码，**没有任何语义色**；输入框聚焦用的是 **2px** 实心描边 `#498A73`（比任何边框都粗一倍，见 `theme.py:21`）。
**Linear：** 状态色成体系（绿/黄/红/蓝），且**永远伴随图标或文字**，颜色只是冗余信息（L7）；聚焦反馈是 1px 边框变亮，极轻。
**性质：** 体系缺失 + 反馈过重。2px 描边在深色背景下会非常刺眼；缺少语义色则导致"成功"和"错误"在视觉上无从统一。

## 3. 目标设计 Token

以下是把上述 9 条规则落到本项目的完整方案。

### 3.0 一个必须先做的决定：强调色用绿还是换靛蓝？

你要求"提取视觉语言，不要复制 Linear 的具体页面结构和业务内容"。强调色正处在这条线的关键位置上：

| 方案 | 说明 |
|---|---|
| A · 换用 Linear 的靛蓝 `#5E6AD2` | 最"像 Linear"，但会让产品在**身份**上变成 Linear 的仿制品——而绿色是这个工具已有的识别色，也是 TOPIK/学习语境更自然的选择 |
| **B · 保留绿色，但重做明度**（推荐） | 保留身份，只移植 Linear 的**用法**：单一强调色、极小面积、低饱和 |

**推荐 B。理由：** Linear 的视觉语言里真正值得学的是"**强调色几乎不出现**"这条纪律，而不是"强调色是靛蓝"这个具体值。保留了绿色，既拿到了纪律，又没丢掉身份。

**具体做法：** 绿色必须整体提亮并降饱和——现在的主色 `#1F6B57` 是深绿，**在 `#0D0E10` 上几乎不可见**。深色背景上的强调色必须比浅色背景下更亮。

### 3.6 与 Linear 原味的刻意偏离 〔v1.3 起，v1.4 重定〕

> **阅读提示：** 下面的 A–D 描述的是 **v1.3 的深色迭代**。v1.4 整体转为浅色后，
> A（中性色带绿调）与 B（降低正文对比度）**已不适用于当前配色**——浅色主题下的
> 对应取值见 §3.1。保留 A–D 是因为它们记录了一个仍然有效的判断过程，
> 且 C、D 两条（强调色承担作用、倒计时用暖色）**在浅色下依然成立**。
> 最新的结论见本节末尾的 **E**。

v1.1 按 Linear 的中性冷黑落地后，实测（决策者反馈）**纯黑不适合长时间学习**。这不是"做得不够像 Linear"，而是 Linear 的使用场景不同：它是给工程师在办公室快速处理信息流用的，而本产品是长时间注视的备考工具。因此有两处刻意偏离：

**A. 中性色带绿色调。**
`#0D0E10` 是中性冷黑，观感偏"终端"。改为暖绿炭 `#101613`，并让侧边栏选中态（`#26332D`）与悬停态带上绿调。

- 呼应本工具**原有的深绿身份**（原侧边栏为 `#173E36`），不是引入新色相
- 绿调在暗环境里比中性灰更不容易显脏，也更耐看
- 结构纪律完全不变：仍然近黑底、仍然 1px 边框承担层级、仍然无阴影

**B. 正文对比度从 15.8:1 降到 12.8:1。**
`#0D0E10` + `#E8E9EA` 是 15.8:1。**对比度并非越高越好**——在深色背景上，过高的对比会让文字边缘产生光晕感，长时间阅读比"不够亮"更累。12.8:1 仍远高于 WCAG AA 的 4.5:1。

**C. 让强调色真正承担作用**（原方案里强调色几乎不出现，实测显得寡淡）：
`连续学习` 指标值用 `accent`；`倒计时` 用 `accent-warm`。两者都是小面积，仍在 §3.1 纪律 1 的 2% 面积限制内。

**D. 为什么倒计时用暖色。**
`PRODUCT_SPEC` 1.3 要求倒计时"增加紧迫感与仪式感"——这需要视觉出口。暖金 `#E8B35E` 同时也是 §6.1 里"保留那一处温度"的落点。**全界面只有这一处暖色**，是刻意的。

**E. v1.4：整体转为浅色。**

深色迭代落地后，决策者的判断是"**纯黑色还是不太适合学习**"，要求改为浅色并放大字号。这是三次色调调整中的第三次：

```
v1.1 中性冷黑 #0D0E10  →  v1.3 暖绿炭 #101613  →  v1.4 浅色 #F6F8F5
```

**这次调整改变了什么、没改变什么：**

| 保持不变（Linear 的纪律） | 随之改变（Linear 的具体取值） |
|---|---|
| 1px 边框承担层级，不用阴影 | 明度方向（深 → 浅） |
| 小圆角（4 / 6 / 8px） | 底色的阶差方向（面板比底更深 → 更浅） |
| 单一强调色，面积 < 2% | `accent` 与 `accent-fill` 合并为一个值（浅色下同一个绿同时满足文字与按钮） |
| 字号跨度窄，层级靠明度承担 | 字号整体上移一档（见 §3.2） |
| 状态色必须伴随图标或文字 | 语义色整体加深（浅底需要更深的色才够对比度） |

**仍然保留的两处"温度"：** `连续学习` 指标值用 `accent`；`倒计时` 用 `accent-warm` `#8A5F12`。这两条从 v1.3 延续下来，浅色下依然成立。

**三次调整共同指向的结论（值得记住）：**

> 色调不是一个"像不像参照物"的问题，而是"配不配使用场景"的问题。
> Linear 的取值服务于**办公室里快速扫读短文本**；本产品是**长时间沉浸阅读韩文**。
> 同一个东西在一种场景下叫"克制"，在另一种场景下叫"费眼"。
> **能移植的是纪律，不能移植的是它恰好选中的那组色值。**

**色彩使用规则（从 Linear 学来的纪律）：**

1. **每屏最多一个实心强调色元素**（一个主按钮，或一个选中态，不并存）。
2. **强调色单个出现面积 < 2% 屏幕**。禁止整块填充。
3. **状态色永远伴随图标或文字**，不单独承载语义（对应 `PRODUCT_SPEC` 9.3 已有的"不依赖单一颜色"要求）。
4. 侧边栏选中态**不使用强调色**——只用 `bg-selected`。

#### 字体加载的路径陷阱 〔实测〕

`QFontDatabase.addApplicationFont()` 传路径时，**路径含非 ASCII 字符会返回 -1**。本项目根目录含中文与韩文，实测四种组合：

| 路径 | 结果 |
|---|---|
| 相对路径（纯 ASCII） | ✓ 注册成功 |
| **绝对路径（含中文/韩文）** | **✗ 返回 -1** |
| 绝对路径（纯 ASCII） | ✓ 注册成功 |
| `addApplicationFontFromData`（Python 读字节） | ✓ 注册成功 |

**解法：用 Python 读取字节再交给 Qt**（`ui/fonts.py`），Python 的文件 IO 正确处理 Unicode 路径。

**该约束的范围（不要过度推广）：** 它**只影响 `addApplicationFont`**。QSS 的 `image: url(<含中文的绝对路径>)` 是**正常工作的**——复选框对勾 `ui/assets/check.svg` 在同样的非 ASCII 路径下能正确渲染（已逐像素验证）。

**拆除全部 emoji，替换为 16px 单色线性图标。已实施（D-3）。**

### 5.2 与已有重构计划的关系

`PRODUCT_SPEC` 第 10 章的路线图里，第 2 期是"数据模型修正与设置页"、第 3~6 期是各模块重构。**视觉改造应当插在第 2 期之后、第 3 期之前**——理由：第 3~6 期会重写 P1~P4 的界面代码，**如果先重构再改视觉，等于把界面写两遍**；先定视觉，重构时直接按新 token 写。

### 5.3 PySide6 的能力边界（必须知道的取舍）

Linear 是 Web 应用。有些效果 **QSS 做不到**，不要在方案里许诺：

| Linear 有 | Qt/QSS 能否 | 处理办法 |
|---|---|---|
| 120ms 悬停过渡 | **不能**（QSS 无 transition） | 接受瞬时变色。视觉损失很小——深色底的瞬时变色本来就比浅色底不突兀 |
| 背景模糊（backdrop-filter） | **不能** | 不做。改用不透明 `bg-elevated` + 边框 |
| 精细的多层阴影 | 困难（`QGraphicsDropShadowEffect` 有性能与渲染问题） | 不做。本方案本来就以边框代替阴影 |
| 亚像素圆角抗锯齿 | 基本可以 | 无需处理 |
| 自定义滚动条 | 可以 | 已实现，保留 |

**结论：本方案刻意不依赖任何 QSS 做不到的效果**，全部改动都是色值、尺寸、边框、圆角——这些 QSS 原生支持。

### 5.6 v1.4 · 字体与浅色主题 〔2026-10-06〕

**新增文件：** `ui/fonts.py`（Pretendard 加载 + 字体栈 + 应用基准字体）。

**改动文件：** `ui/theme.py`（整份调色板转浅色、字号上调、字体栈接入）、`main.py`（注册字体）、`ui/vocab_view.py`（状态提示移入操作条）。

#### 字体

按指示统一使用 `design/Pretendard-1.3.9/`。**关键约束：Pretendard 不含简体中文字形**（实测缺 11/11），因此字体栈为 `Pretendard → 微软雅黑`。`〔v1.6〕`原先此处引的旁证脚本 `单词/单词表转文本PDF工具.py` **已被删除**；该判据现在只由 `ui/fonts.py` 的 `FONT_STACK` 承载。

**踩到并解决的路径陷阱：** `QFontDatabase.addApplicationFont()` 在**路径含非 ASCII 字符时返回 -1**。本项目根目录含中文与韩文，所以按路径加载**永远失败**。改用 `addApplicationFontFromData`（Python 读字节）解决。详见 §3.2。

> **注意这个陷阱的发现方式：** 第一次跑通验证时打印出「已注册族：（未加载）」。如果没有加那句诊断输出，字体会**静默回退到系统字体**——界面照常显示，只是没用上 Pretendard，而且要等到人眼发现"韩文看起来不像 Pretendard"才可能察觉。**加载类操作必须有可观测的成功判据。**

#### 状态提示不再独占一行

`vocab_view.py` 原来把"已载入 N 个单词"作为一个独立行插在操作条与表格之间，会把内容区整体下压。v1.4 移入操作条内（按钮与搜索框之间），不再占用独立行。

顺带修了两处：

| 问题 | 原 | 现 |
|---|---|---|
| 计数不准 | `len(lines)`——把列数不足被跳过的行也算进去 | 统计实际插入的行数 |
| ~~OCR 进度刷屏~~ `〔v1.6 已消失〕` | ~~把子进程原始输出尾部 50 字符贴到界面，又长又不可读，还会撑变形操作条~~ | 当时改为固定显示「正在转换…」；随后整条 OCR 路径被移除，操作条里已无进度标签。**这条诊断仍然值得记**：把子进程原始输出直接贴进操作条会撑变形布局 |

#### 仍然无法自动验证的部分

离屏环境 `QFontDatabase.families()` 返回 **0**——**一个系统字体都加载不到**。因此：

- 截图里所有文字都是方块（此前我误判为"离屏没有中韩字体"，实际是连拉丁也没有）
- **字体栈、中文回退、字号观感、韩文可读性，全部只能由真实窗口确认**
- 唯一可自动验证的是「Pretendard 四个字重注册成功」（已验）与「对勾图标渲染成功」（已逐像素验）

> （离屏下窗口未激活时 `QApplication.focusWidget()` 永远返回 `None`，于是"笔记区
> 聚焦时不接管键盘"被误判为失败）。**先确认断言本身是对的，再怀疑代码**——
> 否则会去"修"一个并不存在的缺陷。

### 5.10 v1.7 补丁 · 词表删除 + 模式按钮互斥 〔2026-10-06〕

**新增色值：零个。** 本轮只新增一条 QSS 规则（`dangerButton:disabled`），取值是既有的
`border` / `text-faint`，§3.1 的 token 表无需改动。

**① 模式按钮的选中态会累积。**

浏览 / 过词 / 专攻三个 `QPushButton` 是 `checkable`，但**不是** `QRadioButton`：Qt 的可选按钮
不会自动成组（`autoExclusive` 默认 `false`），而 `clicked` 是**先把按钮自己的 `checked` 取反、
再发信号**。所以每个点击的默认结果都是"多一个按钮亮起"，而原 `set_mode()` 只把新选中的那个
`setChecked(True)`，从不去动别人 → 三个按钮一路累积，最终**三个全绿且再也退不回去**。

实测复现（离屏、走真实点击路径）：

| 操作 | 修复前选中数 | 修复后 |
|---|---|---|
| 初始 | 1（浏览） | 1（浏览） |
| 点「过词」 | 2 | 1 |
| 点「专攻」 | 3 | 1 |
| 点「浏览」 | 3 | 1 |

修法是 `_sync_mode_buttons()`：每次切换把三个一起重写。**关键在它还覆盖"被拒绝的切换"**——
选中「全部词表」时点「过词」，守卫会拒绝并弹提示条，但那次点击早已把按钮翻成选中；只写
"当前模式"的实现会把这个被拒的按钮留在选中态，用户看到的是"点了没反应、而且它亮着"。

> 这条值得单独记一笔的原因不是它难修，而是**它不可能靠读代码发现**：`setChecked(True)` 看上去
> 完全合理，缺的是"Qt 不会替你取消别人"这条 Qt 侧知识。三个按钮、四个点击路径，只有把状态
> 打出来才看得见。

**② 删除词表。**

数据规则（只删第一层、`word_notes` 不动、删完重导笔记能回来）写在 `PRODUCT_SPEC` 流程 G 的
`〔v1.7 实施裁定〕` 里，此处只记视觉决策：

- 用 `dangerButton` 而不是 `iconButton`。工具条上两个同为次级按钮的相邻控件，用**色相**区分
  比用面积/字重区分更合适——后者会破坏"每屏最多一个实心强调元素"的层级，也会让危险动作显得
  比载入更重要（它不是）。
- **补了 `:disabled` 规则。** `dangerButton` 此前在 `theme.py` 里定义了却从未被任何视图使用，
  因此没有禁用态；而它一落地就有一个真实的禁用场景（「全部词表」不可删）。QSS 里写了 `color`
  的按钮在禁用时**不会**自动变灰，会原样保持危险色，看起来像可点却没反应——所以这条必须显式写。
- 确认框是本页唯一的模态框，门槛判断见 `PRODUCT_SPEC` 流程 G。

**验证：** 删表前后逐表核对 `words` / `word_list_progress` / `word_lists` 行数与 `word_notes`
总数（204 → 204，一条没少）；专门造了"同一个词同时存在于两份词表"的局面，确认删掉其中一份后
该词的笔记、三态、重点标记完整保留；再导入同一份 TSV，确认笔记与三态自动回来、断点归零。
全部跑在数据库副本上。离屏渲染确认工具条未因新增按钮而拥挤（最后一个控件右边界 1035 / 可用 1036）。

## 6. 需要你拍板的取舍

### 6.1 深色会对"备考工具"的气质产生什么影响（**最重要的一条**）

Linear 是**冷峻的专业工具**：给工程师在办公室长时间处理信息流用的，情绪目标是"专注、无干扰"。

但本产品是**个人备考工具**，原始大纲明确要求"**备考倒计时…增加学习紧迫感与仪式感**"，P0 的设计目标是"让今天的学习有一个好开始"。深色 + 全无彩色的界面，客观上是**偏冷、偏压抑**的。

这不是说不能做，而是要说清楚代价与对策：

| 选项 | 说明 |
|---|---|
| **A · 完全照搬 Linear 的冷峻** | 视觉最纯粹，但与"仪式感/鼓励"的产品语气冲突 |
| **B · 移植纪律，保留一处温度**（推荐） | 全部采用 Linear 的克制规则，**只在 P0 首页保留一点温度**：日常完成的 P0 指标行就是那个位置——「今日亮点」与「本周进度」两张纯事实的正向反馈卡（`PRODUCT_SPEC` D1）。若还需一处视觉强调，用倒计时的一个 `accent` 数字或一条极细的 `accent` 进度条。面积控制在 2% 以内，不破坏纪律 |

**推荐 B。** 理由：Linear 的纪律解决的是"界面显得业余"的问题；而"学习需要一点正向反馈"是产品定位决定的，不该被视觉潮流覆盖。

`〔已落地，v1.3〕` **这条担忧被实测证实了，并且比预期的更严重。**

v1.1 按线性方案落地后，决策者的反馈是"**纯黑色确实不太适合学习**"——问题不只是"缺少温度"，还包括：

1. **中性冷黑观感像终端**，不像学习空间
2. **正文对比度 15.8:1 过高**——深色底上过高的对比会让文字边缘产生光晕感，长时间注视反而更累

因此 v1.3 做了三件事（细节见 **§3.6**）：底色改为暖绿炭、正文对比度降到 12.8:1、让强调色真正承担作用。**倒计时用暖金 `#E8B35E`**，是 §6.1 方案 B 里"那一处温度"的落点，同时也回应了原始大纲对"仪式感"的要求。

> **本节的教训值得记下来：** "移植一套成熟产品的视觉语言"不能只移植它的**取值**，还要检查它的**使用前提**。Linear 的低对比、冷峻、近乎无彩，是为"办公室里高效扫读短文本"优化的；换成"长时间沉浸阅读韩文"，同一套取值就从"克制"变成了"费眼"。**移植的对象应当是纪律（少色、小圆角、1px 边框、窄字号跨度），而不是它恰好选中的那几个色值。**

### 6.2 深色还是浅色？ 【已定：浅色】

| 选项 | 说明 |
|---|---|
| A · 只做深色 | 最纯粹，工作量最小 |
| B · 深色为主，浅色为第二主题 | 深色默认、浅色可选。**白天用浅色、夜间用深色**是真实需求 |
| **C · 浅色为唯一主题**（v1.4 采用） | 与 B 的工作量相同，但只维护一套色板 |

**v1.1 先落了深色**（工作量最小）。**v1.3 调暖。v1.4 整体转浅色**——决策者的实测判断是"纯黑色确实不太适合学习"。

**没有采用 B（双主题）的理由：** 双主题需要维护两套完整色板与所有组件的两套状态，是**成倍**工作量。而本产品绝大多数使用发生在白天/室内，浅色单主题已经覆盖主要场景。色值始终**按语义命名**（`bg-surface` 而非 `dark-card`），因此将来要加深色主题时，结构是现成的。

**这条的历史价值：** 它证明了"先只做一套"是正确决策——色调方向被改了三次（冷黑 → 暖绿炭 → 浅色），如果一开始就做双主题，三次调整都要做两遍。

### 6.3 韩文可读性 【已实测通过，2026-10-06】

v1.1 落地时提出：深色底 + 15px 韩文可能笔画发糊，必须真实窗口实测。

**结论：通过。** v1.4 起韩文正文为 **16px**（`koreanText` / `koreanTextEditor`）、P1 单词主词 26px，决策者在真实窗口中确认可读。浅色主题 + Pretendard 的组合也一并确认。

**为什么这一项拖到最后才结案：** 离屏环境 `QFontDatabase.families()` 返回 0——**一个系统字体都加载不到**，截图里所有文字（含拉丁）都是方块。所以字号与字体的观感**从未**能自动验证，只能靠人眼。这条限制写在 §5.6 与 `CLAUDE.md`。

**留给未来的判据：** 如果再动字号或字体，仍然只能用真实窗口确认。**不要因为"离屏截图看起来正常"就认为排版没问题**——离屏截图里根本没有字。
