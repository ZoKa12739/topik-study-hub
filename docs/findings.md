# 发现与决策

## 需求
- 用户希望依照 `docs` 里的设计方案，完善当前较简陋的 TOPIK 学习工具箱；本轮先进行研究并给出方案。

## 研究发现
- 设计提案定义了五个模块：每日计划、单词仓、影子跟读、资料库、知识碎片；目前导航结构已对应这五个模块。
- 当前实现采用 PySide6，依赖中包含 PyMuPDF、ffmpeg-python 与 schedule，但数据层尚未建立，`core/` 目录为空。
- 视觉表现以零散的组件内联样式为主：深蓝侧栏、浅灰主区、纯白卡片与高饱和按钮；缺少统一主题、版式层级、空状态和响应式细节。
- 每日计划仅支持本地 JSON 待办增删与勾选；考试日期硬编码为 2027-04-11，未体现日期配置、历史、统计或跨模块自动记录。
- 单词仓可载入 TSV、调用外部 OCR 脚本、检索并临时高亮重点词；笔记和重点标记均未持久化，OCR 脚本位置指向工作区之外的相邻目录，路径可靠性不足。
- 影子跟读具备文件选择、MP3 播放、A-B 循环与 MKV/MP4 转 MP3 的基本流程；缺少语速、快捷键、字幕/文本导入及音频和文本定位关联，转换进度信号也没有接入界面。
- 资料库只按目录递归扫描文件名并交给系统默认程序打开；尚无标签、全文索引、PDF 内嵌阅读、阅读进度或文件元数据。
- 知识碎片会扫描整棵资料目录下的图片，能显示和 OCR；未实现截图采集、瀑布流、分类、笔记、来源或检索，且大量资料时初始化/浏览体验会变差。
- 当前应用没有统一配置、日志、依赖可用性检测、数据库迁移或错误恢复策略。
- 相邻资料目录确实存在 `写作`、`听力`、`阅读`、`单词`，当前分别包含 21、8、9、23 个文件；以这些目录作为资料库初始映射是可行的。
- 现有 Python 文件可通过语法编译检查；本轮未运行带界面的应用，也未修改应用代码。

## 技术决策
| 决策 | 理由 |
|------|------|
| 本轮不修改应用代码 | 当前目标是形成改版设计方案 |
| 以 SQLite 作为统一数据底座 | 与设计提案一致，能集中管理学习记录、词汇、资料元数据与碎片 |
| 先改善首页与共享基础能力，再深化单模块 | 可让五个模块产生联动，避免继续堆叠孤立功能 |
| 将数据访问集中在 `StudyDatabase` | 页面不再各自读写零散 JSON，后续模块能复用同一数据层 |

## 第 2 期实施发现（2026-10-06）

### 路径耦合已经失效（最重要的一条）
- 资料根目录**实际**在 `课程资料/` 之下两层（写作 21 / 听力 8 / 阅读 9 / 单词 23 个文件）。
- `vault_view` / `snippets_view` 原用「从 `__file__` 向上三级」推导，得到的是 `课程资料/`——
  它下面是分门别类的子目录，**没有**四个科目文件夹。也就是说 P3 与 P4
  在这台机器上一直是坏的，只会显示"找不到资料文件夹"。
- 结论：`PRODUCT_SPEC` D10 的判断被实机证实。改为"探测预填 + 落库配置"（D10-C）后，
  探测函数按限深 BFS 找到了正确目录。
- 词表转换脚本同理：真实位置是 `<资料根>/单词/单词表转文本PDF工具.py`，已随资料根一起配置化。

### 数据
- 真实库迁移前有 49 条 `word_states`（2 条带笔记、0 条星标、49 个互不重复的韩文词），
  1 条 `activity_log`。迁移后全部保留在 `word_notes`，`word_key` 已收敛为 `korean`。
- 因为 49 个 `korean` 互不重复，D2 的"合并键收敛"在这份数据上没有碰撞；迁移代码仍实现了
  碰撞合并（把两份笔记都留下），以备将来。

### 环境
- `ffmpeg` 就绪（7.1）；**`Tesseract` 未安装**——P1/P4 的 OCR 在当前机器上不可用。
  P5 的外部工具自查会如实报告这一点。

### 验证方法
- `compileall` 与离屏构造**都抓不到**"路径指向错误目录"：前者只查语法，后者只走构造。
  有效手段是"复制真实库 → 跑迁移 → 逐条断言"，本轮据此先验证副本、再放行真实库。

## 第 3 期实施发现（2026-10-06）

### 规格内部有一处冲突，必须由实施裁定
- `PRODUCT_SPEC` 4.2 正文写 `Space = 下一个`，D14 写 `Space = 可临时揭示` 释义。
  **两者不能同时成立**，规格本身没有说以谁为准。
- 裁定取 D14。理由不是"哪个更晚"，而是**职责**：判断动作本身立即跳下一个词
  （流程 B 第 5 条"无动画、无确认、无停顿"），所以"下一个"这个键按了无事可做；
  而 D14 用整节论证了"第一遍的标记准确性决定第二遍专攻的对象"。
- 教训：**规格写得再细也会留下互相否定的地方**，而这类冲突只在实现到那一行时才会暴露。
  发现就地裁定并回写两处正文，比留一个"实现和文档对不上"的状态好。

### "重新导入不丢笔记"是一个具体的实现约束，不是口号
- 它要求把 `words`（第一层）与 `word_notes`（第二层）的边界**真的按层划开**：
  导入只重建 `words`，并按 `source_path` 复用 `word_lists` 行。
- 反向也成立：如果按"新建一份词表"处理，用户的断点会留在旧行上，第二次导入就变成
  "笔记还在但进度清零"——比丢笔记更难察觉。

### 存量计数在多词表共享下必然矛盾
- 6.2 定下"状态按**词**而非词表+行"：同一个韩文词出现在两份词表里共用一行 `word_notes`。
- 于是 `word_list_progress` 的 `passed_count` / `marked_count` **不能充当真相**——
  两份词表的计数会同时被同一个词影响。本版改为**读取时实时 join 统计**，
  存量列只在写入断点时刷新一次，纯粹为了让导出文件自洽。

### 三态与断点必须同事务
- `set_word_state` 原来自己 commit；过词要"写状态 + 推进断点"两步。
- 若两步各自提交，中断后会出现"断点过了但状态没记"——用户重进时看到的是一个
  **被静默跳过**的没判过的词。所以拆出**不提交**的 `_apply_word_state`，
  由 `pass_word` 掌握事务边界。`Ctrl+Z` 复用同一个方法：把状态与断点一起写回旧值。

### 离屏环境的一个新陷阱：焦点依赖窗口激活
- `QApplication.focusWidget()` 返回的是**活动窗口**的焦点控件。离屏下若有第二个
  顶层窗口存在，主窗口就不再是活动窗口，`setFocus()` 无声失效，焦点断言全部为假失败。
- 这解释了"笔记区聚焦时不接管键盘"为什么被误判——**不是代码错了，是断言的前提不成立**。
  本轮的第二次同类教训（第一次见上一条"验证方法"）。

### 键盘优先与"别抢输入"是一对约束
- 4.2 要求过词时手不离开键盘；但同一页里有搜索框与笔记编辑区。
- 因此每个键盘动作前面都有一道 `_keyboard_ok()`；`Space` / `Ctrl+Z` 更是**按模式启用**
  （专攻卡的笔记区里，`Ctrl+Z` 必须是文本撤销）。少了这层，写笔记时按 `1` 会把词判出去。
